| direct，0 | 0.2895 | 0.0768 |

每格 n=10、各列分别取中位数。这里没有把 GPU 绝对时间与主机相对时间相减；只能说 B 的提交到回调跨度变化远大于其设备执行区间变化。此跨度包含 commit、设备排队、运行和回调送达，尚不能定位为某一个环节。hidden 较晚才启动 B，此时竞争可能已经结束，因此各组 B 的竞争相位不同，不能把较短跨度解释成 hidden 的优势。

## 下一项对照

保持原三接口与数值工作独立，另建实验而不修改归档二进制：

1. 去掉“等待提升回调才放行 owner”的准备条件。记录 B 真正到达、建立依赖、owner 的优先级观察与清理开始，callback 仅是观察事件，不作为性能测量启动前提。
2. 竞争任务先实际完成至少一段递推，再在仍有声明剩余工作的边界触发 B。保留实际进度、B 到达时的运行区间和剩余工作；这仍是事件锚定条件，不冒称随机开放环到达。
3. device-ready 与真实在途设备工作作为两个独立 phase。后者按保存的 GPU 时间事后判断实际相位；配置名称不能充当执行中证据。
4. 记录提交、scheduled、GPU 起止、CPU completion callback、owner/B 恢复的不同边界。若要比较绝对时刻，先保留并验证原始时钟起点与兼容性；否则只比较各自区间。
5. 同样完整运行所有竞争工作，分别报告 B 延迟和全部 scope drain。没有理由要求三接口的每个样本都按固定快慢排序。

观察者继续通过不含 producer handle 的通知等待，性能区间结束后才 join，避免观察代码向 owner 捐赠优先级。不得把 owner CPU 提优说成 GPU 抢占或已经传播到 Metal 内部服务线程。

本项要分辨的是：请求依赖跨越 Swift task、设备队列和完成服务时，哪些边已由现有运行时表达，哪些环节还需要额外观测或协议；不是先假设需要修改全部执行域。
