# 必要清理与 Swift 等待依赖

固定设备工作与资源协议后，检验同一个前台请求的等待关系如何传到负责资源归还的任务。此阶段关注 CPU 服务与依赖可见性，不从 Swift task priority 推导 GPU 抢占能力。

## 最小情境

GPU 写入 A 拥有的实际 buffer。A 即使收到取消，仍须等待设备完成，完成声明的 CPU 读取／验证，再归还 buffer，B 才能重新写入该 buffer。CPU 读取是实际访问义务，不用 sleep 模拟清理。

采用相同的 owner task、GPU kernel、CPU 读取次数与 buffer 复用路径，比较：

1. 前台高优先级任务直接等待 owner 的 `Task.value`。
2. 前台等待通知式 continuation，等待关系未显式连接到 owner。
3. 同样通知接口，显式向 owner 转发优先级需求。

取消、设备完成、CPU 读取结束、资源释放和 B 的结果分别记录。设置无 CPU 竞争和有可控 CPU 竞争的对照；竞争任务执行固定的真实计算片段，并在声明边界让出，最终必须全部结束。gate 仅安排准备和启动顺序，不用来制造耗时或证明调度公平性。

## 要隔离的因素

先以设备结果已 ready 的情境隔离 CPU 依赖；再加入真实在途设备工作，观察设备等待是否遮蔽 CPU 调度效果。owner 的初始优先级固定为 background，前台需求为 high；记录实际采样的优先级，不凭配置名称断言已发生传播。

主机 CPU 工作量、buffer 身份、提交量和数值必须一致。记录竞争任务开始／结束与计算量，避免一个方案只是少运行了竞争工作。不同调度会改变观察顺序，性能不能作为正确性 PASS 条件。

## 验证和指标

- 实际设备完成之前不进行冲突 CPU 读取；CPU 读取结束之前不让 B 冲突复用。
- task 取消不丢弃必要收尾，完整 scope 最终回收所有任务与设备工作。
- owner 在 CPU 清理开始时的优先级、设备完成到清理开始、清理执行、释放到 B 准入、B 首个结果分开记录。
- 显式／直接依赖是否传播和实际等待是否缩短分别判断。若当前竞争不限制清理，或瓶颈主要在设备，可出现无性能收益。

该实证只能支持特定执行条件下的依赖传播与调度影响。没有类型约束、成本模型与服务假设时，不声称已经获得 PriML 的响应时间定理。
